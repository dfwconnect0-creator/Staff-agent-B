## The Last 10% Problem

This is his most consistent failure pattern at the operational level. Projects reach 90% completion — technically working, planned, partially tested — and then stall on a final step that requires energy or external action he does not currently have. GitHub Actions configuration, client conversion follow-up, publishing a finished piece. The work is done. The shipping is not.

More precisely (from journal patterns): the last 10% is almost always the *audience-facing* or *relationship-facing* 10% — the part that requires being seen, or requires someone else to respond. Infrastructure work that he can close alone tends to ship reliably. Publishing, client follow-up, and delivery-to-a-named-audience are where projects stall.

Any agent working with him must actively watch for this pattern and flag it before the project goes cold.

### The mode matters more than the content

When looking at a day's entry or a morning check-in, it's more useful to identify which *mode* Mohamed is in than to track which project he named. The three observed modes are:

- **Planning mode** — listing, ideating, drawing boxes, collecting specs
- **Production mode** — executing, shipping, closing things
- **Reflection mode** — processing, questioning, noticing patterns

Mode predicts behavior better than project does. A planning-mode day won't produce shipped work no matter what project is named. A production-mode day moves things forward even if the project named is different from yesterday's. An agent calibrating a morning briefing should try to read the mode and match the suggestion to it (planning-mode Mohamed needs one small execution task, not more ideas; production-mode Mohamed needs protection from interruption, not more options).

## Tool-switching — context matters

Mohamed switches tools frequently (napkin.ai + Canva → NotebookLM infographics → Gemini NanoBanana → Remotion + programmatic audio/video; similar churn on the agent layer between Antigravity IDE, Claude CLI, OpenCode CLI, Gemini CLI). This is not inherently a problem.

The observed split: when there's a client or external deadline, tool-switching reflects good judgment (new tools are genuinely better; switching on March 16, 2025 served a SAMCV deadline). When there is no deadline and no external accountability, tool-switching can become the project itself — the week is spent evaluating stacks rather than shipping work.

An agent can usefully ask, when Mohamed mentions switching tools: "what external deadline is this switch serving?" If none, the switch is worth flagging. If there is one, celebrate the pragmatism. *This pattern is held open — more evidence needed before treating it as firm.*
